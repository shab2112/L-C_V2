Lockwood & Carter deployment note

Vercel vs Railway for the Current Backend

Why the current Vercel setup can continue to work, what the real risk is, and when Railway becomes the cleaner backend option.

Executive answer

Vercel is fine for the current web app

The deployed site can continue running on Vercel without a meaningful performance problem at the current stage. The backend pieces that are needed in production have been added as Vercel serverless API routes.

Current state

What is running now

  • React/Vite frontend is deployed on Vercel.
  • Production API calls are handled by files inside the /api folder.
  • The main Express backend still exists in server/index.js, but it is not the primary production server on Vercel.
Key point

This is not mainly a performance issue

The concern is backend consolidation and long-term security maintenance. Vercel can serve these routes well enough now. Railway becomes useful when one central Node backend is better than several serverless copies.

Current backend shape

The project currently has two backend surfaces

Vercel production API

These routes are active in the Vercel deployment:

  • /api/darie-chat
  • /api/house-price-data
  • /api/admin/hp-data
  • /api/_hp-data-utils.js
+

Full local Node backend

The project also has server/index.js, which contains broader backend logic for routes such as leads, enquiries, content studio, email, WhatsApp, market comparison, and house price data.

Meaning: the app is not broken because of this. It simply means some backend logic exists in more than one place.

Concrete project example

House Price Data is the best example

The deployed property intelligence page depends on house price APIs. To make it work on Vercel, similar logic exists in both the Express server and Vercel API files.

Vercel version

api/house-price-data.js api/admin/hp-data.js api/_hp-data-utils.js

These are the routes Vercel can run directly as serverless functions.

Express version

server/index.js

This is the broader Node backend that contains similar route logic plus additional server features.

The actual risk

A fix can be made in one backend file but missed in another

This is the long-term problem with duplicated backend logic. It is not that the current site cannot perform. It is that production behavior may depend on a different file than the one being edited.

Risk example

Admin upload security

If we add admin role verification inside server/index.js but forget to add the same check inside api/admin/hp-data.js, the deployed Vercel route may remain less secure.

Risk example

Data parsing or cache behavior

If the Excel parsing logic is improved in api/_hp-data-utils.js but not in server/index.js, local testing and production behavior can slowly drift apart.

Performance view

Why Vercel can still perform at the same practical level now

Area Vercel current setup Performance impact today
Frontend pages Static Vite build served from Vercel. Very suitable. This is one of Vercel's strongest use cases.
DARIE chat Serverless route forwards requests to NVIDIA API. Fine for normal usage. Most latency comes from the AI provider, not from Vercel itself.
Property intelligence data Serverless route fetches and parses the house price spreadsheet. Acceptable at current traffic. Can be improved later with stronger caching.
Admin upload/update Serverless route writes to Supabase storage/settings. Works for occasional admin usage. Security is the bigger concern than speed.

Conclusion: for the current launch, Vercel is not a performance blocker. The main reason to change later is architectural cleanliness and security consistency.

What Railway changes

Railway would make the backend one central service

Current Vercel-only backend

Vercel frontend -> /api/darie-chat -> /api/house-price-data -> /api/admin/hp-data server/index.js still exists separately
→

With Railway backend

Vercel frontend -> api.lockwoodandcarter.com -> server/index.js -> all backend routes in one place

Railway would run the full Node server continuously. Vercel would only serve the frontend and call Railway for backend work.

What gets corrected

The duplication problem disappears

Concern Current Vercel API folder Railway backend
Security fixes Must ensure both /api and server/index.js are updated when logic overlaps. Fix once in server/index.js. Production uses that same backend.
Private API keys Can be kept server-side in Vercel functions, but spread across separate route files. Centralized in one backend environment.
API growth Each new route may need a separate Vercel handler. New routes are added to the same Node server.
Testing Need to remember which backend surface production uses. Local backend and production backend can match more closely.
Recommended decision

Keep Vercel now, move backend later when it becomes operationally heavier

Use Vercel now

Good current fit

  • The site is primarily a frontend website.
  • The current serverless routes can support the active features.
  • Performance should be fine for the current stage.
  • No urgent migration is needed.
Move later

Railway trigger point

  • Admin tools become business critical.
  • More AI/content workflows go live.
  • Email, WhatsApp, leads, enquiries, and uploads need one secure backend.
  • Maintaining duplicate API logic becomes slow or risky.

Final answer: Vercel can continue running the project without immediate performance issues. Railway is recommended later for backend consolidation, cleaner security, and easier long-term maintenance.

Target future architecture

The clean long-term structure

Vercel

Hosts the public React/Vite frontend at www.lockwoodandcarter.com.

Railway

Runs the Node backend at api.lockwoodandcarter.com, including admin routes, AI providers, email, WhatsApp, leads, and data APIs.

Supabase

Continues handling database, auth, and storage, accessed securely from the backend.
